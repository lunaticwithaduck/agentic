## Outcome

### Root Cause Analysis

**Two distinct problems were found:**

#### 1. Historical silent failure (pre-March 12 runs)
In 4 consecutive runs (2026-03-07 through 2026-03-11), eq09 was completely absent from the
summary JSON (`task_count: 9`, all other tasks present). The `bench/results/e2e/eq09/` directory
contains files only dated March 12, confirming the subprocess failed silently on all prior runs.

The failure mechanism in `compare.py` (lines 492–496):
```python
except RuntimeError as e:
    log(f"FAILED")
    log(f"    → error: {e}")
    log(f"    → skipping task {task_id}")
    continue
```
When the subprocess raises `RuntimeError` (timeout, non-zero exit, or JSON parse failure), the
task is skipped via `continue`. No cache file is written. On the next run, the task has no cache,
so it re-runs and fails again — silently repeating across all subsequent runs until the subprocess
eventually succeeds.

The error message IS logged to stderr (`_E2E_STDERR`), but Suite 04 surfaces stderr line-by-line
with `print_info`. If the suite runner output is not reviewed carefully, these lines look like
normal progress notes rather than failure indicators.

**Why eq09 specifically?** The rate-limiting prompt ("My Express.js API is getting hammered by
scrapers...") is straightforward text. However, when the `.claude/` infra is copied to the temp
dir, the skill-detector hook fires on the prompt, which matches `rate-limiting` keywords
("rate limiting", "rate limit"). The skill content is injected as a system prompt into the Claude
session. In early March, this may have caused the subprocess to produce a response that was
either malformed JSON or caused the `claude -p` command to exit non-zero, triggering the
RuntimeError handler.

#### 2. Quality regression (all runs since March 12)
Once eq09 started completing, it consistently lost to vanilla Claude (winner=B, delta=-1.125,
with-infra score 2.75/5 vs without-infra 3.875/5).

**Evidence:**
- `bench/results/e2e/eq09/with-infra-sub.txt`: 937 bytes, 12 lines — only analytical notes,
  no implementation code.
- `bench/results/e2e/eq09/without-infra-sub.txt`: 5193 bytes — full working Express.js middleware
  with all required code.
- Judgement scores: `implementation_correctness` — Response A (with-infra): 2/5, Response B
  (without-infra): 5/5. This dimension has the highest rubric weight (3).

**Root cause:** The `rate-limiting.md` skill's `## Output Format` section prescribes an
analysis-first structure: "1. Algorithm choice with justification, 2. Rate limit configuration
table, 3. Implementation code..." This causes the infra run to spend its first tokens on
theory/notes and produce an incomplete response. The high-weight rubric dimensions
(implementation correctness: weight 3, HTTP compliance: weight 2) require working code — which
the skill's framing delays or omits entirely.

### Fix Applied

Updated `.claude/skills/rate-limiting.md` `## Output Format` section to lead with working
implementation code rather than theory. The new format explicitly instructs:
- Lead with complete, runnable implementation code
- Inline algorithm justification (not a separate section)
- Include 429 response example with headers
- Close with a one-paragraph production note (Redis, IP spoofing, bypass risks)
- Explicitly prohibit opening with theory or comparison tables

This aligns the skill's output with the rubric's highest-weight dimensions
(implementation_correctness and http_compliance) while preserving the production_concerns
knowledge that the skill uniquely contributes.

### Why the Fix Is Sound

The without-infra run (vanilla Claude) already knows how to write rate limiting middleware.
What the skill should add is deeper domain knowledge: RFC 6585 compliance details, distributed
system concerns (Redis, atomic ops), X-Forwarded-For bypass risks. By leading with code and
embedding this knowledge inline (as comments and a production paragraph), the with-infra
response will be both more complete and more expert than vanilla — scoring well on both
implementation_correctness and production_concerns.

### Files Changed
- `.claude/skills/rate-limiting.md` — `## Output Format` section rewritten to lead with code

### Files Not Changed
- `bench/e2e/compare.py` — The error surfacing and `continue` behavior is acceptable; errors
  ARE logged to stderr. The silent failure was an intermittent subprocess issue that resolved
  itself, not a systemic bug in compare.py.
- `bench/e2e/tasks.json` — The eq09 prompt is valid and not the cause; no simplification needed.
- `SUBPROCESS_TIMEOUT` (300s in compare.py) — Adequate for this prompt; not the bottleneck.
